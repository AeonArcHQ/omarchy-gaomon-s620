# OpenTabletDriver on the S620 (prototype, 2026-10-25)

A test of whether OpenTabletDriver (OTD) can supply what the kernel driver cannot: 90°/270° rotation, a pressure curve and pen button actions (the 🔴 rows in `vendor-app.md`). Nothing here is in the plugin yet; the settings were set by hand with the `otd` console client.

## Setup

- **Observed**: OTD 0.6.7 is not in the Omarchy or Arch repositories; it is in the AUR (`opentabletdriver`, maintainer `gonX`, an OTD core contributor) and on Flathub. The AUR `PKGBUILD` builds the upstream tag tarball; its SHA-256 `95e8fe64…38796f` matches the tarball downloaded from GitHub. `dotnet-sdk-8.0` and `dotnet-runtime-8.0` come from `extra`.
- **Observed**: the package installs `/usr/lib/modprobe.d/99-opentabletdriver.conf` (`install wacom /usr/bin/true`, `install hid_uclogic /usr/bin/true`). While it is installed the kernel driver this plugin uses never loads again; `sudo rmmod hid_uclogic` plus a replug hands the tablet to OTD. Removing the package undoes it.
- **Observed**: the daemon (`systemctl --user start opentabletdriver`) detects `Gaomon S620` (config `Gaomon/S620.json`), maps the full 165.1×101.6 mm to the logical 1536×960 display, and creates `OpenTabletDriver Virtual Artist Tablet`, which Hyprland lists as `opentabletdriver-virtual-artist-tablet`.
- **Observed**: `otd settabletarea` changes only the running settings; `otd loadsettings <file>` replaces them, and `otd savesettings ~/.config/OpenTabletDriver/settings.json` is what persists them.

## Results on the tablet

- **Observed**: cursor, full area and pressure work in Artist Mode (the owner checked with the pressure meter).
- **Observed**: 270° (area 101.6×63.5 mm at the centre, rotation 270) is right with the tablet turned to the right; 90° moves backwards in that pose. The crop keeps the screen's 16:10 ratio, so about 38% of the tablet is used.
- **Observed**: express keys bound to `MultiKeyBinding` `Control+Z` and `Control+Shift+Z` undo and redo in Xournal++. `LinuxArtistModePadBinding` creates `OpenTabletDriver Virtual Pad` (`root:input 0660`, no `uaccess`), which `s620-pad` cannot read without a new udev rule.
- **Observed**: in Artist Mode `MouseBinding` fails: `IMouseButtonHandler unavailable. Your selected output mode is incompatible`. Pen buttons can only be stylus buttons or keys; mouse clicks need the mouse output mode, which has no pressure.
- **Observed (source)**: Hyprland 0.56.2 `CInputManager::onTabletButton` sends pen buttons only through the tablet protocol (`PROTO::tablet->buttonTool`), with no pointer fallback, so apps without tablet support see nothing. The owner keeps them as stylus buttons.
- **Observed**: OTD 0.6.7 ships no filters (`otd listfilters` was empty), and the official plugin repository has no pressure curve. A 30-line filter of ours (`PipelinePosition.PreTransform`, `pressure = (p/max)^Exponent × max`, built against the 0.6.7 `OpenTabletDriver.Plugin` project) loads from `~/.config/OpenTabletDriver/Plugins/<name>/`; with exponent 3 the owner saw a medium press read much lower ("acho que está certo"). The prototype source stays out of the repo for now.
- **Observed**: Hyprland's `input.tablettool.pressure_range_*` does not reach the virtual tablet. With `pressure_range_max = 0.3` sent through `hyprctl eval`, then the daemon restarted (new virtual tablet) and the tablet replugged, a light press in the panel's pressure test still rose gradually instead of reaching 100%. The panel offers no Hyprland pressure range on the OTD backend.

## The plugin on the OTD backend

- **Observed**: with the package installed, `hid_uclogic` blocked and the daemon running, `hid-generic` binds the tablet and creates one unsuffixed input node, `GAOMON Gaomon Tablet` (256c:006d), next to `OpenTabletDriver Virtual Artist Tablet`, `… Virtual Keyboard` and `… Virtual Pad`. `s620-pad` counts only hid-uclogic's `… Pen`/`… Pad` nodes as the kernel backend, and reports `otd` from the USB device plus the virtual tablet. A daemon left running after the package was removed keeps the virtual devices alive with no tablet ("No tablets were detected"); the kernel nodes win then.
- **Observed**: the panel shows "connected · OpenTabletDriver", hides the firmware, and shows mouse mode, the pressure range and the express keys as not available on OpenTabletDriver.
- **Observed**: the plugin reads the running settings with `otd savesettings <temp>`, patches only the S620 profile's `AbsoluteModeSettings`, then `otd loadsettings` and `otd savesettings ~/.config/OpenTabletDriver/settings.json`. Filters and bindings came back unchanged (only `1.0` written as `1`). "Match screen" (162.6×101.6 mm centred on the 16:10 screen) and a custom area dragged to a corner both limited the pen as drawn (owner: "tudo certo").
- **Observed**: 180° with a custom area drawn in the lower right of the panel's drawing (77×48.1 mm, centre 105, 64.9 as held) is sent as `Tablet.Rotation = 180` with the centre mirrored to 60.1, 36.75; with the tablet turned (keys at the bottom right) the pen worked only in the lower right as held, and moved the right way (owner: "tudo certo").
- **Observed**: the shell's plugin reload does not recreate a plugin's service; changes to `Service.qml` need `omarchy restart shell` before a test.
- **Observed**: the plugin binds the four express keys to `LinuxArtistModePadBinding` "Pad Button 1".."Pad Button 4" (`otd savesettings` read back `["Pad Button 1","Pad Button 2","Pad Button 3","Pad Button 4"]`). Before the new udev line the virtual pad was `root:input 0660` and the panel said "no permission on the express keys"; after reinstalling the rule `getfacl` shows `user:<you>:rw-`, the helper reports ready on the OTD backend, and each express key lights its own dot in the panel (owner: "sim, acende"). With the default actions, in the browser's address bar key 1 undid typing, key 2 redid it, key 3 (eraser, `E`) typed "e", and key 4 showed the key functions notification (owner: "sim, tudo funciona").
